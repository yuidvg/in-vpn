# in-vpn の目的

作成日: 2026-10-06（JST）／更新日: 2026-10-07（JST）  
状態: 目的と受け入れ条件の定義。2026-10-09に[部分CLI](implementation.md)を実装したが、以下の必須要件全体は未達。要件を部分モードへ読み替えない。

## 実現したいこと

macOSで、現在のディレクトリ・ファイル・ツールをそのまま使いながら、指定したコマンドまたはシェルと、その子孫プロセスの通信だけを指定VPNへ流す。

```sh
in-vpn vpn1 command arg1 arg2
in-vpn vpn1 shell
```

`vpn1` は設定済みVPNプロファイルの名前。`command` は実行したいコマンドの位置を表し、固定のサブコマンドではない。`shell` はVPN内で対話シェルを開始する操作を表す。プロジェクト名は `in-vpn`、この作業ディレクトリ名は `in_vpn` とする。

VMやコンテナへ開発環境を移すこと、Mac全体のVPNを切り替えること、各ツールへ個別にプロキシを設定することを、通常の利用手順に要求しない。

利用例は、通常のターミナルとVPN内のターミナルで、同じ `curl` や開発ツールを同時に使い、それぞれ異なる通信経路を選ぶこと。通常のブラウザや別のターミナルは、それまでの経路を使い続ける。

## 満たすべき要件

| ID | 要件 | 完了と判断する条件 |
| --- | --- | --- |
| R1 | いつもの作業環境で実行できる | cwd、ファイルへのアクセス、PATH、通常の環境変数、引数、標準入出力を維持する。終了コード、シグナル、対話シェルのジョブ制御が機能する |
| R2 | 実行単位で対象を選べる | 実行ファイル名・パスが同じでも、指定した実行とその子孫だけを選ぶ。短命な子、exec、親の終了、PID再利用を扱える |
| R3 | プロキシ非対応の通信も扱う | 対象の外向きTCP・UDPを指定VPNへ転送する。IPv4・IPv6を検証し、扱えない経路は直接通信させず遮断する |
| R4 | 名前解決もVPN内で行う | 対象の標準的な名前解決が指定VPNのDNS経路を使い、対象外のアプリのDNS設定・経路を変えない |
| R5 | 障害時に直接通信へ戻らない | VPN、転送処理、制御プロセスの停止・クラッシュ、起動前後の隙間でも対象通信を遮断する。保護を準備できなければコマンドを実行しない |
| R6 | 複数VPNを同時に選べる | `vpn1` と `vpn2` のセッションを並行実行しても通信・DNS・障害の影響が混ざらない |
| R7 | 対象外の通信を維持する | VPN内外で同じツールを同時に使える。無関係なアプリの接続・名前解決を、正常時にも対象VPNの障害時にも維持する |
| R8 | 開発とマシン設定を分ける | このリポジトリで製品を開発し、nix-darwin側には導入・マシン設定・起動設定を置く |

ここでいう「直接通信」は、対象プロセスの通信が指定VPNを通らず宛先へ到達すること。VPNバックエンドがVPNサーバーへ送る暗号化トンネルの外側の通信は、必要な通信として区別する。

## 対象とする範囲

最初の対応環境はmacOS。VPNの初期候補はWireGuard、通信バックエンドの初期候補はsing-box、透過的な通信処理の初期候補はNetwork Extensionとする。いずれも目的を満たす手段として評価し、採用だけで要件達成とはしない。

対象は `in-vpn` から新規に起動したプロセスと、その実際の子孫が開始する通信。親シェルが終了しても、残った子孫が直接通信へ切り替わってはならない。

既存のDockerデーモン、既存のブラウザ、launchdなどへIPCで依頼して別プロセスに行わせる通信は、単なる子孫追跡では対象にならない。初期版では自動対応を約束せず、対応範囲と利用上の制限を明示する。起動前から存在する外部向けソケットの持ち込みも、通常のファイル継承とは分けて扱う。

ICMP・`ping`、raw socket、待ち受けサーバーへの外部からの接続、他OS対応、特権を使った意図的な保護回避への対抗は初期版の提供範囲外。ただし、未対応プロトコルをVPN外へ黙って通してよいという意味ではない。非対応通信の遮断方法も検証する。

UNIXドメインソケットによるローカル資源の利用は維持する。loopbackやLANのIP通信は、直接通信を許すかによって保証が変わるため、初期案では自動的な例外にせず、VPN経由または遮断とする。直接アクセスが必要になった場合は、例外を目的・設計・事前実験・受け入れ検証へ明示してから追加する。

## リポジトリの分担

| 場所 | 管理するもの |
| --- | --- |
| この独立リポジトリ | CLI、macOSアプリ、プロセス追跡、Network Extension、VPNバックエンドとの接続、テスト、ビルド・配布手順、パッケージ定義 |
| nix-darwinリポジトリ | ビルド済み製品の導入、マシンごとの設定、必要なサービスの起動設定 |

VPNの秘密鍵や署名用秘密情報はGit・Nix storeへ入れない。既存のmirror用設定は参考実装として扱い、この製品の開発に伴って既存ジョブの経路や運用を変更しない。

## 最初の到達点と完成の区別

まず [事前不確実性テスト](feasibility.md) で、macOSの権限・発生元識別・子孫追跡・DNS分離・障害時遮断を小さな独立実験で確かめる。製品CLIや常駐アプリを作り込む前に結果を集め、その結果から採用方式を決める。実験と製品の置き場は [directory-layout.md](directory-layout.md) に定義する。

最初のVPN経由の実証は、**同じ実行ファイルを内外のシェルから起動し、片方だけVPNへ流せるか**。試験用ランチャーで実施でき、完成した `in-vpn` を前提にしない。名前や実行パスによる一括振り分け、プロキシ環境変数に依存する成功では合格としない。

この検証が成功しても、子孫追跡、DNS、障害時の遮断、TCP・UDP、複数VPNの要件を満たしたことにはならない。「小さな常駐アプリ」で完結するかも未確定である。

事前実験の成立は製品の完成を意味しない。完成の判断は、実装後に行う [verification.md](verification.md) の必須検証と証跡に基づく。必須要件を満たせないと判明した場合は、制約を示して目的または方式を再検討する。プロキシ専用wrapperなどへの変更を、同じ目的を達成したものとして扱わない。
