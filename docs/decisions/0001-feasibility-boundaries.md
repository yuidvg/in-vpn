# 0001: フローの選別と遮断の責務を分けて検証する

日付: 2026-10-07。状態: 実測に基づく部分判断。製品構成全体の採用決定ではない。

[追加実験](../evidence/feasibility/20261007-tailscale-off/report.md)で、同一バイナリのTCP・UDP各100組について、既知PIDの選別と受信結果が一致した。システムcurlもIPv4・観測したNAT64経路で選別できた。したがってNetwork Extensionのaudit tokenをフローの識別候補として継続検証する。PIDだけの登録は試験専用とし、製品には世代を含む識別と子孫の所属管理が必要である。

透明Providerを終了させると、それまで拒否していた同じBプロセスの新規TCPが直接届いた。外部HTTPSでも、クラッシュ後にBの10回中8回でHTTP 200を確認した。よってProvider単独をR5の遮断境界には採用しない。再起動監視だけでも保護の根拠にしない。別の機構で対象の保護を維持し、機構自身の故障・通信開始前の競合・継承ソケット・通常側への影響を検証する。

[初回実験](../evidence/feasibility/20261007-initial/report.md)で反証された「現在のPPIDと定期一覧だけによる追跡」「接続済みFDを制御しないsandbox単独」も採用しない。これは他のイベント追跡方式や、FDの扱いを含む複合方式が不可能という結論ではない。

標準getaddrinfoの元PIDは取得できたが、同じドメインルールでdigの通信は捕捉されなかった。標準リゾルバー、直接DNS、共有キャッシュを分けて評価する。ドメインルールだけで全DNSをVPN別に分離したとは扱わない。

次の採用条件は、独立した遮断、子孫追跡、DNS分離、通常ソケットからVPNへの透明転送を同時に実証すること。目的の縮小や、プロキシ対応wrapperへの置き換えはこの判断には含めない。
