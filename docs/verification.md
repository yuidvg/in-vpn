## 合否の共通ルール

- 状態は `未実施`・`実施不能`・`失敗`・`合格` を使う。未実施と実施不能を合格に含めない。
- 合格には、再現手順、実機環境、期待値、観測結果、証跡を必要とする。
- 対象の成功だけでなく、同時に動く対象外の経路と動作も確認する。
- 外部IPの表示だけで漏れなしとはしない。送信前からのパケット観測と、管理下の受信サーバー・DNS側の記録を照合する。
- 対象データの直接送信、別VPNへの混入、対象外の巻き込みは、1回でも観測すれば失敗とする。
- 試験中の漏れゼロは、その条件での観測結果である。競合や故障時も遮断が維持される仕組みの説明とコード確認を合わせ、有限回の試験だけで絶対保証とはしない。

## 検証環境と証跡

本番ジョブや利用者の実データは使わず、識別可能なテストIDと合成データを使う。

| 項目 | 用意・記録する内容 |
| --- | --- |
| 実機 | macOS版とビルド、CPU、Xcode/SDK版、署名・entitlement、OS承認状態 |
| 実装 | コミットまたはソースのハッシュ、CLI/ProviderのビルドID、sing-boxの実バージョン、秘密を除いた設定とそのハッシュ |
| VPN | vpn1/vpn2の識別可能な出口とVPN内DNS。出口IPが共有される場合はVPNサーバー側の観測も用意する |
| 試験サーバー | 管理下のTCP/UDP受信先、IPv4/IPv6アドレス、接続元とテストIDを記録する機能 |
| DNS | 管理下のテストドメインとリゾルバー側の観測。試験ごとに未使用の名前を作り、キャッシュだけの成功を避ける |
| クライアント | 同一ハッシュ・同一パスの、プロキシを参照しない通常のBSDソケット（TCP/UDP）試験プログラム。`SOCK_RAW` とは区別し、通常のCLIツールも別途確認する |
| 観測 | Providerの分類記録、プロセス生成・終了の記録、関係する物理/トンネル/loopbackインターフェースのキャプチャ、受信側ログ |
| 対照群 | 同じ試験を通常シェルから並行実行する。対象外の名前解決と長時間接続も維持する |

パケット観測では、宛先への直接TCP SYN・UDP・DNSと、VPNサーバーへの暗号化トンネルを区別する。対象通信の成功前後だけでなく、起動前、障害直前、再起動後、子孫の終了まで記録する。経路を観測できない、またはキャプチャ欠落が大きい場合は漏れなしと判定しない。

実行ケースは `verification/cases/`、生の証跡は `.local/runs/acceptance/<run-id>/`、確認・秘匿処理を終えた報告は `docs/evidence/acceptance/<run-id>/` へ保存する設計とする。配置と役割は [directory-layout.md](directory-layout.md) に定義する。時刻・テストIDで突合できるようにし、パケットやログの秘密情報を除去してから共有する。この文書の更新時点では試験プログラム・証跡ファイルは存在しない。

## G1: 同じ実行ファイルの片方だけをVPNへ流す

実装後の最初の経路分離判定は **V02** とする。事前段階ではF01/F05で同じ問いを最小構成で調べておく。DNSは別の検証で切り分けるため、この段階の通信先は管理下のIPv4リテラルを使う。

1. 通常シェルで試験プログラムを実行し、その環境の元の経路を記録する。既存VPNがある場合も含めて対照群の基準にする。
2. `in-vpn vpn1 shell` から、まったく同じパス・ハッシュの試験プログラムを実行する。
3. 通常シェルとVPN内シェルで同時に接続する。`HTTP_PROXY`・`HTTPS_PROXY`・`ALL_PROXY` 等の大小文字双方を外し、プログラム自体もプロキシを使用しない。
4. テストIDごとに、発生元プロセス、所属、宛先、受信側の接続元を照合する。
5. シェルを作り直す場合と同じシェルを使う場合を含め、内外の同時実行を100組繰り返す。実行順序も入れ替える。

| ID | 合格条件 | 要件 | 状態 |
| --- | --- | --- | --- |
| V02 | 対象側だけがvpn1を通り、対象外は元の経路を維持する。初回パケットを含め、対象の直接送信・混入が0件 | R2, R3, R7 | 未実施 |

ファイル名やパスで両方がVPNへ流れる、専用の別バイナリだけがVPNへ流れる、プロキシ対応クライアントでしか成功しない場合は失敗。V02合格だけではDNS・全子孫・故障時遮断・UDP対応の完了にはしない。

## G4: 障害時にも直接通信させない

対象と対象外から継続送信しながら、次の故障を個別に発生させる。新規接続と既存接続の双方を含め、起動中・通常運転中・終了処理中の各段階で繰り返す。

| ID | 故障・条件 | 合格条件 | 要件 | 状態 |
| --- | --- | --- | --- | --- |
| V10 | 不明なVPN、無効な設定、権限不足、Provider未起動、VPN到達不能 | 実コマンドを起動せず非ゼロ終了。起動有無は通信だけでなく試験用ファイル書き込みでも判定する | R5 | 未実施 |
| V11 | sing-boxの停止・強制終了、WireGuard peer不通 | 対象はエラーまたは遮断となり直接通信0件。対象外と別VPNの通信は維持される | R5, R6, R7 | 未実施 |
| V12 | Providerの強制終了・無効化、制御サービス/追跡処理の停止、同時故障 | 故障検出までの隙間を含め対象の直接通信0件。停止したプロセス自身に依存しない遮断の証拠がある | R5, R7 | 未実施 |
| V13 | Wi-Fi切断・再接続、ネットワーク変更、スリープ復帰、サービス再起動 | 生存対象を通常経路へ解放しない。安全な復旧または明示的な失敗となり、古い所属を誤適用しない | R2, R5, R7 | 未実施 |
| V14 | Providerが転送を拒否する分岐、対象判定不能、バックエンドの認証失敗 | 対象を明示的に閉じる。透明プロキシで `false` を返して直接通信させる分岐がないことをコードと実機で確認する | R5 | 未実施 |

少なくとも各故障・各段階を20回反復し、注入時刻と最初のエラー／遮断時刻を記録する。再起動後に成功したことだけを障害時遮断の証拠にしない。

## 実施順と完成判定

最初にF系列の事前実験と方式選定を行う。その結果に基づく製品を実装した後、この文書のG0→G1→G2/G3/G4→G5/G6を実施する。事前に得た成立条件が製品でも保たれるかを再確認し、特にDNS分離とクラッシュ時遮断の未解決を、UIや配布作業の完成で埋め合わせない。

初期版の完了にはV00〜V25の必須項目の合格が必要。非対応範囲を含む試験は「安全に拒否し、制限が明記されること」を合格条件とする。TCP・UDP、標準DNS、子孫追跡、障害時遮断、複数VPNは、黙って対象外へ移さない。未実施の必須項目が残る場合は検証版と表示する。

試験結果には次の形式を使う。

```text
run-id / 試験ID:
実施日時（JST）:
機体・OS・ビルド・署名・バックエンド版:
設定（秘密を除く）:
手順と故障注入位置:
期待する経路・遮断・対象外の動作:
実際の観測と反復回数:
証跡のパス:
判定（未実施 / 実施不能 / 失敗 / 合格）:
残る制約・再検証条件:
```

現時点で完了しているのは目的・設計候補・事前不確実性テスト・ディレクトリ設計・製品受け入れ検証の文書化のみ。F系列・V系列の実施と `in-vpn` の実行機能は、まだ確認されていない。
