# Tailscale切断後の事前実験（2026-10-07）

**既知のプロセスを選別してTCP・UDPを止めることは成立した。一方、透明Provider単独の障害時遮断は反証された。** 製品CLI、子孫追跡、VPNへの透明転送、完全なDNS分離は完成していない。

実施環境は初回と同じmacOS 27.0.1（26A434）、arm64、Xcode 27.0。ユーザーがTailscaleを切断し、`scutil --nc list` でも切断を確認した。SIPやシステムDNSは変更していない。TailscaleのExtension登録自体は残るため、未導入端末の試験ではない。既存VPNの有無だけを原因と結論しない。

## 主な結果

| 条件 | 観測 | 設計に使える範囲 |
| --- | --- | --- |
| 同一Cバイナリ、毎回新しいA/B、TCP・UDP各100組 | Aの200ペイロードを受信、Bは0。400フローすべてでaudit tokenのPIDと判断が一致 | 既知の起点PIDを選ぶ限定条件は成立。子孫・PID再利用・VPN転送は含まない |
| システムcurl、nc、Cの外向きTCP | IPv4と観測したNAT64宛先を含めると、同じバイナリのBだけ接続拒否 | システム提供バイナリも対象にできる。この試験ではVPN転送はしていない |
| getaddrinfoで新しい試験用DNS名を解決 | A/Bそれぞれの元PIDを取得。Aは名前なし応答、Bは遮断して8秒で打ち切り | 標準リゾルバーの要求元を保持した通知の実例。VPN別回答・キャッシュ分離は未確認 |
| digによる直接DNS | A/BともNXDOMAINを取得、ドメイン限定ルールの通知0 | ドメインルールだけで任意のDNSパケットを捕捉できるとは扱わない |
| Providerをabortで強制終了 | 一時的にA/Bがタイムアウトした後、Bの直接TCPを受信。外部HTTPSでも10回中8回HTTP 200 | Provider単独ではR5を満たさない。再起動の監視だけを保護の根拠にしない |

## F01: 通知0件の原因と、記録の訂正

切断直後の2回では設定保存が30秒でタイムアウトした。[初回](../20261007T064707Z-F01-5ec115/report.md)、[再試行](../20261007T064800Z-F01-56c233/report.md)。後者は1組だけ実行でき、A/B成功・通知0だった。設定を毎組削除・再作成する手順を、一度作ってIPCで試験PIDを変更する手順へ改めた。保存待ちの部分出力も保存するようにした。

TCP/UDPを別ルールにした0.0.4でも、通常curlの3組は通知0だった。[実行](../20261007T065327Z-F01-a015a3/report.md)。同じProviderでCの外向きTCP/UDPには通知が来て、TCPのBだけが接続拒否となった。[C試験](../20261007T065506Z-F01-e92c56/report.md)。この相違を一つのProvider稼働中に比較したところ、通常curlの実接続先は `64:ff9b::101:101`、`--ipv4` のcurlは `1.1.1.1` だった。IPv4だけのルールでは後者だけが捕捉され、Cとncも捕捉された。[比較実験](../20261007T065816Z-F01-ceda50/report.md)

観測した `64:ff9b::101:101` は、IPv4/IPv6変換用の既知プレフィックスへ `1.1.1.1` を埋め込んだ形式に一致する。[RFC 6052](https://www.rfc-editor.org/rfc/rfc6052)

0.0.5以降では、観測したNAT64の単一宛先 `/128` とIPv4 `/32` の指定ポートにルールを限定した。0.0.6での再試験では、通常curl・IPv4指定curl・nc・Cすべてに通知があり、各Bだけを拒否できた。[両アドレス族の比較](../20261007T070642Z-F01-26957f/report.md)

**初回報告と古いrunの「外向きIPv4」という表現は、URLのIPリテラルからの誤推定だった。** その時点ではremote_ipを保存していないため、過去の個々の接続のアドレス族は断定できない。今回の対照試験ではNAT64によるルール不一致を再現・解消した。初期ループバック条件はAPI・ルール・待機手順も変えており、初期の通知0をすべて同じ原因には帰属させない。過去の生データは書き換えず、この訂正を添える。

UDPは送信後すぐ閉じる旧プローブでは、対象外Aも届かなかった。[旧手順](../20261007T065607Z-F01-8b55f1/report.md)。受信を別スレッドで行いUDP echoを待つ手順にすると、[5組](../20261007T070101Z-F01-816318/report.md)と別起動の[100組](../20261007T070129Z-F01-42155a/report.md)でTCP・UDPとも期待どおりに選別できた。短命なUDPソケットについては別の未解決条件として残し、OS一般の保証に読み替えない。

100組試験は0.0.5のProvider、IPv4ループバック、通常ユーザー、既知PIDをIPCで登録する条件。受信欠落・重複・予期しないB受信・A側エラーは0、audit token欠落／PID不一致も0。各組のA/Bは同じパス・ハッシュのバイナリを使い、シェルからexecした。PID世代の寿命管理や子孫の自動所属判定は試していない。VPN出口の相違を確認した試験でもない。

## F03: 標準DNSの要求元は取得できたが、分離全体は未実証

0.0.6のProviderに `invpn-feasibility.example.com` 配下だけのDNSルールを追加し、新しい別々の名前をA/Bから解決した。getaddrinfoではA/Bそれぞれに2件ずつ、元プロセスのPIDと署名ID `dns-probe` を持つUDP通知が来た。Aは `EAI_NONAME`、Bは受理・クローズの対象となり、8秒でテスト側が終了させた。共有システムサービスのPIDしか得られない、という結果ではなかった。[実験](../20261007T070725Z-F03-427778/report.md)

同じ条件のdigはA/BともNXDOMAINを得たが、通知は0だった。DNSドメインルールでこの直接ソケット通信まで分類できるとはいえない。getaddrinfoも今回は別々の新規名だけで、同名の同時要求、共有キャッシュ、回答のVPN別分離、URLSession、全DNS名を扱うルール、VPN内への転送は未検証。Bのタイムアウトを「VPNで正しく名前解決できた」という成功にしない。

## F04: クラッシュ後の直接通信

最初の故障注入ではProviderのPID消失を確認したが、その後のconnectが3秒以内に返らずハーネスが終了した。[初回](../20261007T070810Z-F04-12c0ee/report.md)。この実行だけで漏れがないとは結論しない。

接続を500msで観測終了できるプローブへ変更して、同じA/Bプロセスを生かしたまま再試験した。稼働中はAだけが届きBは拒否、試験Providerの `abort()` 後は元のPIDが消えた。直後の接続は詰まり、その後10回のB試行中6回のペイロードが受信側へ届いた。設定削除はこれらの受信を記録した後に実行した。[完走した故障試験](../20261007T071000Z-F04-59b33b/report.md)

別起動の[再確認](../20261007T071122Z-F04-cc5ae6/report.md)でも10回中6回のB直接受信を記録した。さらに外部HTTPSで確認した。最初は[設定保存待ち](../20261007T071800Z-F04-0a807f/report.md)、次は[故障注入IPCの応答待ち](../20261007T072013Z-F04-a9550e/report.md)で中断した。これらも失敗記録として残す。IPC応答の成否とProvider PIDの消失を別々に記録する手順へ直し、[外部試験を完走](../20261007T072422Z-F04-bc36d0/report.md)した。

外部試験は同じlibcurlバイナリのA/Bを生かしたまま、要求ごとに新しいTLS接続を作り、証明書を検証し、明示的にプロキシを使わず `https://1.1.1.1/cdn-cgi/trace` へ接続した。Provider稼働中はAがHTTP 200、Bは接続拒否。abort後に元のProvider PIDが消え、最初はタイムアウトし、その後Bの10回中8回でHTTP 200を受け取った。実接続先は今回もNAT64のIPv6だった。これは外部サーバーの内部ログではなく、クライアントが受けたTLS検証済み応答による証拠である。

この結果は、独立した保護がない透明Provider構成の反証である。ループバック上の新規IPv4 TCPと、観測したNAT64経路の外部HTTPSによる反例であり、外部への全経路・UDP・他のIPv6条件・既存接続を網羅した試験ではない。障害時に対象外Aも一時的に影響を受けた。通常停止でBの直接通信が再開することも旧ループバック試験で観測した。

## 次に解く設計上の依存

- **独立した遮断:** Providerが消えても対象プロセスの保護を維持する具体的なOS機構が必要。sandbox単独では継承済みFDの反例があるため、先行するソケットやIPCの扱いを含めて検証する。
- **子孫:** 手動PID指定から自動追跡へ進む。Endpoint Securityの権限は現在不足しており、新しいdescendants APIのイベント取得は未実施。
- **DNS:** 今回の要求元情報を使い、管理下の応答、同名キャッシュ、直接DNSも含めた分離を試す。
- **VPNへの透明転送:** 既存のF05はSOCKS対応プローブとWireGuardのバックエンド試験。NEが受けた通常ソケットをVPNへ中継する実験は残る。
- **複数VPN:** 2本目の独立した検証用VPNと、上記の分離が必要。F07/F08は未実施。

F系列全体の合格、V系列の合格、製品方式の採用とはしない。

## 証跡と後始末

各runにソース保存版・ハッシュ・コマンド結果・受信記録・Providerイベント・cleanupを残した。0.0.6からは導入済みHost/Providerのバイナリハッシュもmanifestへ加えた。公開版のaudit tokenは長さとハッシュに置換し、生値・詳細なOSログは `.local/` のみに保存した。パケット採取は行っていない。

0.0.6への更新後に一度 `saveToPreferences` がpermission deniedとなった。[失敗記録](../20261007T070430Z-F01-fd65b4/report.md)。ユーザーが再試行を了承した後に設定保存と追加試験が成功した。OSの許可を回避する実装はしていない。

試験プロセスと受信機は終了し、各試験のネットワーク設定は削除した。試験アプリと承認済みSystem Extension 0.0.6/6は再検証用に残る。古い版はOSによる再起動時の削除待ちを含む。Tailscaleの再接続や既存mirrorの変更は行っていない。WireGuard設定は `.local/secrets/wg-CH-FREE-8.conf` のまま、親700・ファイル600・Git除外で保管している。
